# Milestone Design

Use this reference to decide whether a milestone is the right planning primitive and to produce a concise but operational milestone description.

## What a Milestone Represents

A milestone is a finite delivery boundary that groups work toward one coherent outcome.

Good milestone purposes include:

- a versioned release
- a launch or rollout
- a migration cutover
- a delivery phase with a concrete exit condition
- a coordinated cross-item target date

A milestone is not automatically the right container for every collection of work.

## Milestone vs Other Planning Primitives

### Issue or work item

Use an issue for one independently actionable unit of work.

Do not create a milestone when the user only needs one bug, feature, or task tracked.

### Epic or parent work item

Use an epic or parent item for a larger initiative that needs hierarchy and can span multiple delivery boundaries.

An epic may contain work across several milestones.

### Iteration or sprint

Use an iteration or sprint for recurring timeboxed planning.

Do not replace a repository's established iteration cadence with milestones merely because both can have dates.

### Release

A release represents a shipped version, tag, artifact, or release record.

A milestone can coordinate the work required for a release, but the milestone is not the release itself.

### Project or board

Use a project or board for ongoing tracking, status views, prioritization, or a broad backlog.

A milestone should eventually complete.

## Naming

Inspect existing milestone names before choosing a title.

Prefer the repository's established pattern, for example:

- `v2.4.0`
- `2026.09 Release`
- `Authentication Migration`
- `Public Beta`
- `Phase 2: Cutover`

Avoid vague titles such as `Next`, `Phase 1`, `Cleanup`, or `Backlog` unless that exact pattern is an intentional repository convention.

Do not rename an existing milestone solely to match a generic naming preference.

## Scope Quality

A milestone scope is strong when a reviewer can decide whether a candidate item belongs without needing additional conversation.

Include:

- the target outcome
- included product, service, or repository surfaces
- explicit exclusions for nearby work that could be confused with the milestone
- objective exit criteria

Avoid:

- copying full issue specifications into the milestone
- listing unrelated nice-to-have work
- using the description as the only source of membership truth
- broad goals with no completion boundary

## Dates

Dates are planning commitments, not estimates generated by the skill.

Acceptable date sources:

- an explicit user-provided date
- a published release or launch date
- a repository or group calendar
- an established iteration or release cadence with an unambiguous computed boundary

Unacceptable date sources:

- issue count
- total issue weight
- story points
- Golden Pounds or Golden Points
- time estimates
- the current date plus an arbitrary duration

### GitHub

GitHub milestones provide a due date, but no native milestone start-date field.

If a start date matters, use an existing repository convention outside the milestone field only when that convention is discoverable. Do not claim a description line or Project field is a native milestone start date.

### GitLab

GitLab project and group milestones provide native start and due dates.

Use ISO dates and preserve the intended calendar date.

## Membership

Native milestone assignment is authoritative.

For each candidate item:

1. verify it belongs to the outcome
2. inspect whether it already belongs to another milestone
3. move it only when the requested plan requires reassignment
4. preserve cross-project scope rules
5. verify the resulting membership

A milestone creation request alone does not authorize creating missing issues or merge requests.

When work is not yet represented remotely, report it as an unresolved planning gap or create it only if the user explicitly requests work-item creation.

## Exit Criteria

Exit criteria describe the milestone outcome, not merely issue state.

Weak:

- all tasks done
- release complete
- testing finished

Strong:

- all required migration paths are deployed and legacy writes are disabled
- supported clients are compatible with the new API contract
- rollback has been validated and release monitoring is active
- all committed milestone issues are closed and no release-blocking defects remain open

Use at least two objectively verifiable criteria for non-trivial milestones.

## Lifecycle

### Open or active

Keep the milestone open while committed work is still in progress or while exit criteria are not met.

### Closed

Close when the milestone is complete or intentionally ended according to repository policy.

Closing is not equivalent to deleting. Preserve completed planning history unless deletion is explicitly required.

### Reopen or activate

Reopen only when work genuinely resumes under the same milestone boundary. If the outcome materially changed, consider whether a new milestone is more accurate.

## Milestone Description Template

Do not leave bracketed instructions in the final description.

```markdown
## Outcome

[Describe the concrete delivery outcome and why this milestone exists.]

## Scope

### In scope

- [Included capability, system, repository, or delivery boundary.]

### Out of scope

- [Nearby work explicitly excluded.]

## Exit Criteria

- [ ] [Objective criterion that must be true before the milestone is complete.]
- [ ] [Second independently verifiable completion criterion.]

## Work Inventory

### Committed

- [Issue, PR/MR, epic, or work item reference when useful. Native membership remains authoritative.]

### Deferred or excluded

- [Related work intentionally outside this milestone, with destination when known.]

## Dependencies and Sequencing

- [External dependency, predecessor milestone, release gate, or sequencing constraint.]
- [Use N/A with a reason when there are no material dependencies.]

## Risks and Mitigations

- **Risk:** [Failure mode, uncertainty, or delivery risk.]
  **Mitigation:** [Prevention, detection, containment, or fallback.]

## Delivery or Release

- [Release, tag, environment, launch, rollout, or cutover relationship.]
- [Use N/A with a reason when the milestone is not release-oriented.]

## References

- [Roadmap, release plan, epic, project, ADR, design, incident, or authoritative documentation.]
```

## Draft Metadata

For draft-only work, keep structured metadata separate from the Markdown description:

- platform
- repository or group
- milestone title
- state
- start date and source
- due date and source
- member item references
- items that would be moved from another milestone
- release linkage

Do not embed metadata in prose when a native remote field will hold it after creation.

## Validation Checklist

Before mutation, verify:

- the title matches the target's naming pattern
- the milestone does not accidentally duplicate existing scope
- the chosen primitive is actually a milestone
- project/group/repository scope is correct
- dates are justified
- committed work is bounded
- exit criteria are checkable
- existing item milestone assignments were inspected
- destructive promotion or deletion is not being inferred
